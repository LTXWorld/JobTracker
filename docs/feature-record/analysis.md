# 平台插件化“投递记录”功能分析（Record-from-Website）

## 背景与目标
- 背景：用户在各招聘网站（智联、51job、BOSS直聘、Moka 等）完成投递后，需要回到平台再次“添加投递并填写信息”，存在重复劳动与数据丢失风险。
- 目标：通过浏览器插件/扩展，在用户投递时即刻抓取职位信息并一键写入平台“投递记录”，减少手工录入，提升记录完整性与时效性。
- 成果度量（Success Metrics）：
  - 新增投递记录中“由插件创建”的占比 ≥ 60%。
  - 用户人均“手动添加投递”次数下降 ≥ 50%。
  - 单条记录平均填写用时 ≤ 10 秒（含确认）。
  - 重复记录率 ≤ 3%。

## 用户画像与关键场景
- 用户画像：活跃求职者、秋招/春招同学、社招用户，有较高多平台同时投递需求。
- 关键场景：
  1) 在招聘网站打开职位详情页，点击“立即投递/申请”前后，插件检测并弹出“是否记录到平台”。
  2) 插件预填公司、职位、链接、来源站点、抓取到的薪资/地点，默认“投递日期=当前时间”，用户确认一键提交。
  3) 未登录平台或离线→本地暂存队列，网络可用时后台补交；已存在相同记录→提示去重策略。

## 范围与非范围
- 范围（MVP）：
  - Chrome/Edge 插件，覆盖常见站点：zhaopin.com、51job.com、zhipin.com、mokahr.com。
  - 基础字段抓取：公司、职位、站点、职位链接、地点、薪资（若可）、JD 摘要（可截断）、投递日期、备注（可选）。
  - 用户登录授权：使用平台现有 OAuth/JWT；插件复用已有 token 存储刷新逻辑。
  - 投递记录创建：调用后端 /api/v1/applications 的 Create 接口。
  - 去重与冲突处理：URL+公司+职位+日期 的规则去重，冲突弹窗合并/忽略。
- 非范围（后续版本）：
  - 自动识别“企业属性（央国企/私企等）”——MVP 采用用户默认配置或提交前选择。
  - 邮箱解析、移动端分享组件、桌面助手等多入口同步。
  - 高级解析（OCR、JS 逆向、抓包 API 回放）。

## 数据与字段映射（平台后端 → CreateJobApplicationRequest）
- 目标接口：POST /api/v1/applications（已存在）
- 必填字段：
  - `company_name`：解析自职位详情页公司名；无法解析时允许用户输入或沿用上次公司名。
  - `position_title`：解析职位标题。
  - `company_attribute`：MVP 通过插件设置页默认值或弹窗选择（避免创建失败）。
- 可选字段：
  - `application_date`：默认“当前日期”；允许用户修改。
  - `salary_range`：解析“x-x k/月/年”文本并规范化（正则提取）。
  - `work_location`：解析地点字段；可做多选/多地合并。
  - `job_description`：抓取 JD 文本（上限长度，避免超大 payload）。
  - `contact_info`：页面可见 HR 联系方式（若有）。
  - `notes`：用户备注；可自动拼接“来源域名/抓取方式/时间戳”。
  - 其他：`follow_up_date`、`interview_time` 等由后续流程补充。

## 抓取策略与站点适配
- 通用优先级：
  1) 结构化数据：页面中的 JSON-LD（JobPosting）和 OpenGraph meta。
  2) DOM 选择器：各站点的稳定 CSS 选择器；提供“训练模式”让用户手动映射（本仓库 content.js 已具备）。
  3) 兜底提取：文案模式匹配（公司/职位/薪资/地点关键词）。
- 站点适配策略：
  - 为每个域名维护 Adapter（轻量 JS 模块）输出标准化 JobPosting 对象。
  - 适配器应尽量无侵入、易回滚；失败时回落到通用提取。
  - 监测 URL 变化与 SPA 路由；在“点击投递”按钮事件附近尝试二次抓取，修正字段。

## 提交与同步流程
1) Content Script 解析页面 → 标准化职位数据。
2) Background 接收消息 → 补全元数据（来源域、抓取时间、用户默认 company_attribute）。
3) 去重检查：
   - 规则：同一用户、同一来源 URL 或（公司+职位）在同一日期存在记录。
   - 操作：覆盖、跳过、创建新条（需明确提示）。
4) 调用后端 Create 接口 → 返回成功后提示“已记录”，支持跳转平台查看。
5) 离线/未登录：存 IndexedDB 队列，周期任务自动补交；重试带指数退避。

## 鉴权与安全
- 延用现有扩展的 token 桥接与刷新逻辑（background.js 已实现）。
- 后端已支持 CORS 与 Chrome 扩展请求（见 backend/CORS_UPDATE_GUIDE.md）。
- 隐私合规：
  - 仅在受支持域名启用解析；尊重用户显式点击同意后发送。
  - 采集范围透明可见；敏感信息（手机号/邮箱）默认不上传，需用户确认。
  - 本地数据加密存储（可后续版本加入）。

## 失败与回退
- 解析失败：展示“快速添加”对话框，用户手填少量必填字段后提交。
- API 失败：写入本地队列并重试；重复失败提示用户检查登录或网络。
- 站点改版：适配器监控错误率，快速热修（通过远端配置或插件热更新策略，后续版本考虑）。

## 风险与缓解
- 风险：页面结构频繁变动、站点反爬策略、字段不全导致创建失败。
- 缓解：
  - 多级解析与兜底；提供用户“训练模式”快速标注字段映射。
  - 将 `company_attribute` 作为插件设置项（默认值）或提交前选择。
  - 监控异常率并建立适配器优先级回退。

## 与“迁移添加投递功能到插件”的取舍
- 同意方向：将“添加投递”的核心表单迁入插件弹窗是合理的，能降低跳转成本。
- 建议：
  - 保留最小化表单（仅必填+少量可选），并尽量靠自动提取预填。
  - 平台 Web 端仍保留完整编辑页，供后续补充丰富信息与跟进状态。

## 成本预估（MVP）
- 工期：1.5–3 周（1 前端/扩展、1 后端、0.5 QA/文档）。
- 站点适配：首批 3–4 个域名（每域 0.5–1 天，含测试）。

## 验收标准（MVP）
- 支持 4 个主流站点抓取并提交成功。
- 无登录时提醒并引导，登录后自动重试；离线可排队。
- 提交前确认弹窗可编辑必填字段；提交后 3 秒内反馈。
- 后端可见投递记录，字段映射正确；重复提交控制有效。
