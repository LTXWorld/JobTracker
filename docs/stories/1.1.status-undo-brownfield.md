## 故事标题
状态撤销功能 - Brownfield Addition

## 用户故事
**作为** 频繁维护岗位进度的求职者，  
**我想要** 在误把岗位状态拖拽或更新到错误阶段后可以立即撤销最近一次变更，  
**从而** 避免错误状态干扰进度追踪与统计分析，节省手动修复时间。

## 故事上下文
- 集成对象：后端 `StatusTrackingService` 与 `StatusTrackingRepository`、前端状态看板（`KanbanBoard.vue`）和快速更新对话框（`StatusQuickUpdate.vue`）。
- 技术体系：Go + PostgreSQL JSONB 状态历史；Vue 3 + TypeScript + Pinia 状态管理；Ant Design Vue 消息与通知组件。
- 复用模式：沿用现有状态更新事务、版本校验、历史记录写入与前端刷新流程。
- 触达接口：`POST /api/v1/job-applications/{id}/status`、新增撤销接口（建议 `/v1/job-applications/{id}/status/undo`）以及 `status_history` 最新记录。

## 验收标准

**功能要求**
1. 用户在看板拖拽或快速更新完成状态修改后，可在提示消息中看到“撤销”操作（例如 10 秒倒计时），点击后回到修改前状态。
2. 撤销成功后，前端看板列、岗位详情时间轴与状态历史全部同步还原，相关备注与元数据恢复到撤销前的一致状态。
3. 若撤销条件不满足（如版本冲突、历史记录不匹配或超时），系统需提示失败原因且保持当前状态不再变更。

**集成要求**
4. 后端提供受保护的撤销接口，仅允许针对当前用户拥有的岗位撤销最近一次状态变更，并在 `status_history` 中记录 `undo` 标记元数据。
5. 撤销操作更新 `status_version`、`last_status_change`、`status_history` 与 `status_duration_stats`，避免重复写入或丢失历史，确保事务回滚一致性。
6. 撤销成功后前端需清理对应岗位的历史缓存、重新获取分析数据，并在 Pinia Store 中保证数据源只来源于刷新结果。

**质量要求**
7. 新增 Go 单元测试覆盖撤销服务逻辑（含最新记录校验、事务提交、冲突处理）以及仓储交互分支。
8. 增补 API/集成测试验证撤销端点在成功、超时、版本冲突等路径下的响应；更新相关接口文档。
9. 前端增加组件或 Pinia Store 的单元/端到端测试，验证撤销按钮显示、点击流程及失败提示；文档或用户指南同步说明新功能。

## 技术备注
- **集成方式**：在 `StatusTrackingService` 增加“撤销最近一次状态更新”方法，读取最新历史记录并基于快照恢复；`status_tracking_handler.go` 暴露对应路由，并沿用认证与错误包装。
- **前端实现提示**：在 `KanbanBoard.vue` 与 `StatusQuickUpdate.vue` 中，将 `message.success` 替换为 AntD `notification` 或具备 `btn` 操作的 `message`，绑定 `撤销` 回调触发 API；注意倒计时与多次点击防抖。
- **状态校验**：撤销需校验 `status_history` 最新项确为当前状态，且版本号与请求前一致，避免跨设备或批量操作导致的错回滚。
- **并发注意事项**：若用户在撤销窗口内再次更新状态，应取消前一次撤销入口；可通过在 Pinia Store 中记录最新操作 token 解决。
- **日志与审计**：撤销时在历史记录 `metadata` 写入 `{"undo": true, "undo_by": user_id, "reverted_to": old_status}`，便于审计与可视化展示。

## 风险与兼容性检查
- **主要风险**：并发或跨终端状态更新导致撤销错用旧快照。
- **缓解策略**：综合使用 `status_version` 校验与最新历史 ID 比对，撤销失败时提示用户刷新再试。
- **回滚方案**：若撤销接口出现故障，可临时下线路由或在前端隐藏撤销按钮，数据库保留历史记录无需额外回滚脚本。

**兼容性确认**
- [x] 无破坏性 API 变更，新增接口保持向后兼容。
- [x] 若涉及数据库修改，仅为附加索引或标记字段，保持可逆。
- [x] UI 延续现有 Ant Design Vue 交互与色彩规范。
- [x] 性能影响可忽略，撤销只读取最近记录并复用现有缓存逻辑。

### 现场问题追踪
- 用户回报撤销 HR 面到三面时出现 `不允许的状态转换`，后端响应 500。
- 复核代码后确认 `UndoJobStatus` 未设置 `jobview.allow_backward` 标志，数据库层阻止回退写入。

### 影响与风险
- 所有回退方向的撤销将失败，验收标准 1、4、5、6 被打破。
- 历史记录会保留 `undo` 记录但状态未回滚，用户体验与数据一致性受损。

### 建议的后续动作
- 在 `UndoJobStatus` 事务开始处调用 `tx.SetLocalFlag("jobview.allow_backward", true)` 并补充单元测试模拟触发数据库限制。
- 修复后重新执行回退→撤销链路验证，再次提交 QA 复核。
