## Story
**As a** 持续推进面试流程的求职者，  
**I want** 在结束某一轮面试并推进到下一阶段前被提示记录本轮体验，  
**so that** 我能系统化沉淀面试感受，及时复盘并为后续求职决策提供参考。

## Acceptance Criteria
1. 当当前状态属于 `一面中`、`二面中`、`三面中`、`HR面中` 中任意一项且用户通过拖拽或快速更新尝试变更状态时，系统需先弹出“面试体验反馈”模态；模态包含评分（好/一般/差）、备注输入、跳过反馈选项及可选跳过原因，用户可取消并保持原状态不变。
2. 用户提交评分（`skip=false`）时，前端需在 `UpdateStatusRequest.metadata.interview_experience` 中写入评分、备注、`recorded_at`（ISO 8601）、`from_status`、`to_status` 与 `recorded_by` 占位字段，保证后端落库后时间轴立即展示完整体验信息。
3. 当用户选择“跳过反馈”时，请求体仍需写入 `skip=true`、`skip_reason`（可选）及基础上下文字段；若选择跳过但未提供原因，界面需给予最小化提示（如 `placeholder`）而不强制填写。
4. 看板拖拽、快速更新弹窗与状态详情弹窗共享同一反馈流程；为两类流程分别补充单元/组件测试，验证评分与跳过分支均会生成正确 `metadata`，且取消操作不会触发接口调用。

## Dev Notes
### 面试体验写入约束
- 后端 `prepareInterviewExperience` 会在缺省情况下写入 `skip=true`，仅当 `metadata.interview_experience` 提供 `skip=false` 且包含合规评分时才记录有效体验；跳过路径允许携带备注与原因。[Source: backend/internal/service/status_tracking_service.go:767]
- `shouldCaptureInterviewExperience` 以“当前状态（旧状态）”判断是否需要捕获体验，因此前端在推进 `一面中` → `二面中`、`一面通过` 等任意流转前都需触发反馈收集。[Source: backend/internal/service/status_tracking_service.go:762]

### 前端状态更新流程
- 看板拖拽通过 `handleDragChange` 直接构造 `{ status: newStatus }` 并调用 Store 更新，需在此处判断并挂起请求流程。[Source: frontend/src/views/KanbanBoard.vue:787]
- `StatusQuickUpdate`（含详情弹窗复用）同样在本地构建请求后立即提交，需加入反馈收集与取消处理逻辑，确保多入口体验一致。[Source: frontend/src/components/StatusQuickUpdate.vue:359]
- Store 层 `updateApplicationStatus` 目前仅透传参数，可在调用前新增工具方法生成 `metadata`，避免重复拼装；同时保留现有撤销、刷新逻辑。[Source: frontend/src/stores/statusTracking.ts:301]

### 请求结构与前端约束
- `UpdateStatusRequest` 已暴露 `metadata` 字段，可直接附带 `interview_experience` 嵌套对象；类型定义位于 `frontend/src/types/index.ts`。[Source: frontend/src/types/index.ts:460]
- 评分枚举值应与后端校验保持一致（`good`/`average`/`bad`），记录时间建议使用 `dayjs().toISOString()` 并统一写入 UTC。
- 为避免重复提交，可在反馈模态内判断数据是否未变化或为空；取消时务必恢复拖拽卡片至原列或重置下拉选项。

### Testing
- 前端测试框架为 Vitest + Vue Test Utils，相关测试可放置于 `frontend/tests/components` 与 `frontend/tests/stores`；运行命令 `pnpm test -- --runInBand` 或 `npm run test`。[Source: frontend/package.json]
- 建议为反馈模态编写交互测试，模拟选择评分、填写备注、点击跳过与取消等路径；Store 层可通过 Mock API 验证 `metadata` 构造。
