# Story 1.2: 面试体验数据模型与 API 扩展

## Status
Done

## Story
**As a** 维护岗位进度的求职者，  
**I want** 在推进面试阶段状态前记录上一轮的面试体验反馈并由后端可靠存储，  
**so that** 我可以在后续复盘和统计时查看完整的面试体验历史并优化求职策略。

## Acceptance Criteria
1. 当 `PUT /api/v1/applications/{id}/status` 处理从 `StatusFirstInterview`、`StatusSecondInterview`、`StatusThirdInterview`、`StatusHRInterview` 等面试阶段状态流转时，允许请求体的 `metadata.interview_experience` 携带 `rating`（取值 `good`/`average`/`bad`）、可选 `note`（≤200 字符）、`skip`、`skip_reason`、`recorded_at` 字段；若 `skip` 为 `false` 且缺少 `rating`，返回 400 并提示缺失评价。
2. 成功写入状态后，`StatusTrackingService` 在同一事务内将经过清洗的 `interview_experience` 信息写入追加的 `StatusHistoryItem.Metadata`，以便 `GET /api/v1/applications/{id}/status-history` 能返回完整评价记录。
3. 新增 `interview_experiences` 表（字段含 `id`、`application_id`、`from_status`、`to_status`、`rating`、`note`、`skip`、`skip_reason`、`recorded_by`、`recorded_at`、`created_at`），并在状态更新事务中插入对应记录；若 `skip=true` 则允许 `rating` 为空。
4. 提供 `GET /api/v1/applications/{id}/interview-experiences` 端点，按时间倒序返回该岗位的评价列表（含评分、备注、跳过原因），并复用服务层聚合方法。
5. 对于未携带 `interview_experience` 的请求保持向后兼容：保留既有状态更新行为，同时写入一条 `skip=true` 的评价记录以标注该次操作跳过反馈。
6. 为成功、缺失评分、跳过、读取接口等场景补充或更新 Go 单元测试/集成测试，确保覆盖率满足现有测试策略要求。

## Dev Notes
### Previous Story Insights
- 上一故事在 QA 复盘中强调 `UndoJobStatus` 必须正确设置 `jobview.allow_backward` 并维持状态历史写入，变更时需避免破坏该事务逻辑。[Source: docs/stories/1.1.status-undo-brownfield.md#QA Results]

### Data Models
- `job_applications.status_history` 使用 JSONB 保存 `history` 数组，记录状态、时间戳、备注与元数据，可存储面试体验信息。[Source: architecture/job-status-tracking-system-architecture.md#状态历史数据结构]
- `StatusHistoryItem` 结构含 `Metadata map[string]interface{}` 字段，可扩展写入评价评分等自定义键值。[Source: architecture/job-status-tracking-system-architecture.md#StatusHistoryResponse]
- 面试阶段状态包括 `StatusFirstInterview`、`StatusSecondInterview`、`StatusThirdInterview`、`StatusHRInterview` 等，需要基于状态机限定适用场景。[Source: architecture/job-status-tracking-system-architecture.md#状态转换规则引擎]

### API Specifications
- `PUT /api/v1/applications/{id}/status` 接口支持 `metadata` 字段，需在请求体验证状态转换、备注长度与元数据有效性。[Source: architecture/job-status-tracking-system-architecture.md#状态更新接口]
- `GET /api/v1/applications/{id}/status-history` 用于返回历史记录与分析数据，新评价应体现在返回的 `metadata` 字段中。[Source: architecture/job-status-tracking-system-architecture.md#状态历史查询接口]
- 新增的 `GET /api/v1/applications/{id}/interview-experiences` 应复用既有认证头与分页/排序约定，保持 RESTful 风格。[Source: architecture/job-status-tracking-system-architecture.md#API架构设计]

### Component Specifications
- 架构文档未针对本后端故事定义新的前端组件指引，相关交互将在后续前端故事中实现。

### File Locations
- 后端服务遵循 `backend/internal/{handler|service|model}` 的分层结构，状态更新相关逻辑集中在 `status_tracking_service.go` 与 `job_application_handler.go`。[Source: architecture/architecture-analysis.md#4.-后端架构分析]
- 数据迁移与数据库访问位于 `backend/internal/database`，需要在此处添加新表迁移。[Source: architecture/architecture-analysis.md#4.-后端架构分析]

### Testing Requirements
- 架构测试策略要求为服务层关键路径编写单元测试，覆盖成功与失败分支，并在必要时使用测试数据库隔离环境。[Source: architecture/job-status-tracking-system-architecture.md#测试策略]
- 状态更新逻辑测试需验证历史条目长度、元数据写入与错误消息内容，参考现有 `StatusTrackingService_UpdateStatus` 测试案例结构。[Source: architecture/job-status-tracking-system-architecture.md#测试策略]

### Technical Constraints
- `StatusInputValidator` 当前仅允许特定 `metadata` 键，扩展时需在清理逻辑中增加白名单并进行长度校验，防止 XSS 与畸形输入。[Source: architecture/job-status-tracking-system-architecture.md#2.-输入验证与清理]
- 状态更新事务使用数据库会话保持一致性，新增写入必须在同一事务内完成以避免历史记录与评价数据不一致。[Source: architecture/job-status-tracking-system-architecture.md#批量操作优化]
- 需遵循 Epic 的兼容性要求，对未携带评价的请求保持旧流程并标记跳过原因，避免破坏现有客户端调用。[Source: docs/epics/1.2.interview-experience-feedback-brownfield.md#Compatibility Requirements]

### Testing
- 后端使用 Go + testing + testify 断言进行单元测试，结合 `setupTestDB` 等辅助工具构造隔离环境。[Source: architecture/job-status-tracking-system-architecture.md#测试策略]
- 新端点可通过集成测试或 handler 测试验证认证、响应结构与排序逻辑，必要时模拟请求上下文。[Source: architecture/job-status-tracking-system-architecture.md#测试策略]
- 需保持覆盖成功、校验失败、跳过记录及数据读取等关键场景，确保满足质量门槛。[Source: architecture/job-status-tracking-system-architecture.md#测试策略]
